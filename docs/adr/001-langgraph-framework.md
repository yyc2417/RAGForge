# ADR-001：为什么选择 LangGraph 作为 Agent 编排框架

> **状态**：已采纳
> **日期**：2026-06-08
> **决策者**：宇诚

## 背景

Agentic RAG 需要一个框架来建模 Agent 的决策流程：查询分析 → 策略选择 → 检索 → 质量评估 → 生成 → 幻觉检测，且包含条件分支和循环（检索质量不够时需要改写查询重试）。

需要评估哪个框架最适合这个场景。

## 备选方案

### 方案 A：LangGraph
- **概述**：LangChain 生态中的状态图框架，将 Agent 工作流建模为有向图，节点是函数，边可以是条件的
- **优点**：
  - 原生支持条件边和循环，直接表达"评估不够好 → 改写 → 重新检索"的逻辑
  - 状态（TypedDict）强类型，每个节点的输入输出清晰可追踪
  - 内置可视化工具（`draw_mermaid_png`），面试时可直接展示架构图
  - 与 LangChain 生态深度集成，复用已有的 Retriever/LLM 封装
  - 社区活跃（GitHub 10k+ stars），文档质量高
- **缺点**：
  - 学习曲线比直接写代码稍高
  - 版本迭代快，API 可能变动
- **决定**：选，完全匹配需求

### 方案 B：CrewAI
- **概述**：面向多 Agent 协作的高层框架，角色驱动的 Agent 团队
- **优点**：
  - 抽象层更高，上手更快
  - 天然支持多 Agent 协作
- **缺点**：
  - 项目定位是单 Agent 自主决策，不是多 Agent 协作，与 CrewAI 设计目标不匹配
  - 简历中已有 AgentForge（多智能体项目），技术栈重复
  - 对单个 Agent 内部的条件循环支持不够精细
- **决定**：不选，定位不符

### 方案 C：纯手写状态机
- **概述**：不用框架，直接用 Python 的 while 循环 + if/else 实现状态转移
- **优点**：
  - 零依赖，完全控制
  - 代码量最小
- **缺点**：
  - 无法直接可视化状态图
  - 缺少状态序列化（无法暂停/恢复）
  - 面试时展示价值低（只是普通代码，没有架构感）
  - 需要手动处理重试上限、超时等边界条件
- **决定**：不选，展示价值和工程完备性不足

## 决定的理由

LangGraph 是唯一同时满足以下条件的方案：
1. 原生支持条件边和循环（RAG 质量评估闭环的核心需求）
2. 强类型状态追踪（决策过程可审计，面试重点）
3. 可生成可视化架构图（面试现场展示）
4. 与已有 LangChain 生态组件无缝集成

此外，LangGraph 是当前 AI Agent 领域的主流框架（LangChain 官方推荐），写在简历上有技术认可度。

## 风险与缓解

| 风险 | 可能性 | 缓解措施 |
|------|--------|----------|
| API 版本变动 | 中 | 锁定 langgraph 版本，用稳定 API |
| 过度依赖框架 | 低 | Task 5 完成后手写一份等价实现（理解原理） |
| 状态机设计错误导致死循环 | 中 | 硬编码 max_iterations=3，框架级 recursion_limit 双重保护 |
