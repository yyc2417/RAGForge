# Web API 设计

## RESTful API 的设计原则是什么？

REST 用统一的资源语义组织 API：

1. **资源化 URL**：名词复数路径（`/users`、`/users/42`），动词用 HTTP 方法表达
2. **HTTP 方法语义**：GET 读（幂等）、POST 建、PUT 全量替换（幂等）、PATCH 局部更新、DELETE 删（幂等）
3. **无状态**：每个请求自带全部上下文（认证凭据），服务端不存会话，便于水平扩容
4. **版本化**：`/api/v1/users` 或请求头 `Accept: application/vnd.api+json; version=1`

## HTTP 状态码应该怎么用？

**2xx 成功**：200 OK（通用）、201 Created（POST 创建成功，配 Location 头）、204 No Content（删除成功无返回体）。

**4xx 客户端错误**：400 参数非法、401 未认证（没登录/token 无效）、403 已认证但无权限、404 资源不存在、409 冲突、422 语义校验失败、429 请求过频。

**5xx 服务端错误**：500 内部异常、502 上游网关错误、503 服务暂不可用（可配 Retry-After）。

原则：4xx 说明客户端要改，5xx 说明服务端要修；错误响应体应含结构化 detail 而非堆栈。

## JWT 认证的工作流程？

JWT（JSON Web Token）由三段 Base64 组成：**Header.Payload.Signature**。Signature 用服务端密钥对前两段签名，防篡改。

**流程**：
1. 客户端登录，服务端校验凭据后签发 JWT（含 user_id、过期时间 exp）
2. 客户端存 token（Authorization: Bearer <token>），随每个请求携带
3. 服务端**无状态校验**：验签 + 查过期，不需要查会话存储

**注意**：JWT 签发后无法主动撤销（到期前一直有效），需要撤销场景用短期 access token + 长期 refresh token，或维护黑名单。Payload 只是 Base64 不是加密，不要放敏感明文。

## API 限流有哪些算法？

1. **固定窗口计数**：每分钟最多 N 次，实现最简单，但窗口边界可能突发 2 倍流量
2. **滑动窗口**：按最近 N 秒精确计数，平滑边界问题
3. **令牌桶**：恒速生成令牌，桶满丢弃；允许短时突发，最常用
4. **漏桶**：恒速放行请求，强制整流

工程实现：单机用内存计数器，分布式用 Redis + Lua 保证原子性；超限返回 429 + `Retry-After` 头。

## 幂等性为什么重要？

幂等 = 同一请求执行一次和多次效果相同。网络重试无处不在（超时重发、消息队列 at-least-once），非幂等接口重试会导致重复扣款、重复建单。

**保证手段**：PUT/DELETE 天然幂等；POST 用客户端生成的**幂等键（Idempotency-Key）**，服务端按键去重；数据库层面用唯一约束兜底。
